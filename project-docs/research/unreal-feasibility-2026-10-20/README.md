# Defender in Unreal Engine: feasibility research

20 October 2026. Research only; no Unreal installation, editor launch, connection, asset import, migration or build was performed.

**Yes: our team could plausibly recreate Defender in current Unreal Engine, using its official MCP for editor work alongside ordinary source editing and compilation.** The evidence supports high confidence in basic game feasibility and conditional confidence in automation. It does not establish a one-click port, identical pixels, improved frame rate or a delivery schedule. Reusing our authored content and rules would save substantial reconstruction; the JavaScript runtime, WGSL renderer and DOM interface would need native equivalents.

The latest released major version verified is **Unreal Engine 5.8**. The newest official hotfix found is **5.8.3, released 22 September 2026**. Pin that version for a trial, then recheck available fixes before starting. [Epic release announcement](https://www.unrealengine.com/news/unreal-engine-5-8-is-now-available), [Epic 5.8.3 announcement](https://forums.unrealengine.com/t/5-8-3-hotfix-released/2833315).

**What MCP changes.** Epic now ships first-party Unreal MCP as an Experimental feature. Enable `ModelContextProtocol` and `AllToolsets`; discover capabilities through `list_toolsets`, inspect schemas with `describe_toolset`, then invoke `call_tool`. Editor calls execute serially on the game thread. Coverage is incomplete and APIs can change. Python/C++ custom toolsets fill gaps; new C++ `UFUNCTION` declarations require an editor restart. Normal registry discovery is editor-only, although explicitly registered runtime hosting is possible. Our recommendation is to keep packaged gameplay independent of MCP. [Epic Unreal MCP documentation](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-mcp-in-unreal-editor).

Epic's own setup reference explicitly includes Codex configuration and an optional macOS arm64 proxy. That establishes a documented connection route; it does not prove our present session can control Unreal. No Unreal MCP connection is registered here, and no live tool catalogue was inspected. [Epic setup reference](https://github.com/EpicGames/unreal-engine-skills-for-claude-code-plugin/blob/main/skills/unreal-mcp/references/setup.md).

The practical workflow would combine filesystem access, a supported C++ toolchain, reproducible builds and editor automation. Python is useful for import and content preparation, but Epic's Python integration runs in the editor rather than shipped gameplay. Use C++ for the simulation and performance-sensitive systems, with Blueprint/UMG for presentation and editable tuning. This architecture is our recommendation, not a tested project. [Epic Python documentation](https://dev.epicgames.com/documentation/en-us/unreal-engine/scripting-the-unreal-editor-using-python).

**What we already own.** A read-only inventory found 68 model JSON sources and 18 level sources, including the sixteen campaign levels, 64 waves and 1,084 scheduled enemy spawns. Play currently exposes three defence families; other model studies and preview systems are not automatically campaign features. Sources use `defender.model` v3 and `defender.level` v4. Models retain palette materials, face overrides, emission/light flags, parent relationships and pivots. The existing mesher compiled six representative model families, including articulated units and missiles; all 86 source-file hashes remained unchanged. [Inventory script](inventory.mjs), [full results](inventory.json), [run summary](inventory.log).

These checks prove accessible source data and working current-format meshing. They do **not** prove Unreal import, animation, lighting or performance. The live design and code take precedence over older milestone counts and superseded requirements in the historical notes. [Design](../../design-doc.md), [project brief](../../project-brief.md), [visual constraints](../../visual-style.md), [rendering](../../rendering.md).

| Defender component | Proposed Unreal equivalent | Main fidelity work |
| --- | --- | --- |
| Grid models and scenery | Generated Static Mesh assets, shared palette materials, instanced repeated scenery | Preserve exposed faces, flat normals, overrides and clean silhouettes; avoid an Actor per voxel. |
| Rigid articulated parts | Component hierarchies initially; assess skeletal representation where useful | Reproduce parent pivots, aiming axes, recoil and existing ordinary gaits. |
| Terrain, paving, water and bridges | Imported authored meshes and explicit level data | Preserve exact stepped heights, clearings, route footprints and solid/water precedence. |
| Waves, ownership and economy | C++ simulation with data assets or validated imported tables | Preserve unlocks, prices, misses, rewards, deployment and transfers. |
| Targeting and projectiles | Custom native controllers and collision queries | Preserve claims, LOS, burst commitment, missile phases and timing. |
| Smoke, sparks, blasts and trails | Niagara plus explicit transient lights/materials | Match bounded lifetimes, intensity curves and approved components. |
| Overview and Drone | Camera components driven by a ported director | Preserve framing, clearance, anticipation, pause and immediate mode changes. |
| Command-panel GUI | UMG/widgets backed by runtime state | Recreate grouping, model portraits, hover identification/ranges and keyboard focus. |
| Distant biomes and water appearance | Separate background geometry and custom material setup | Match softness/darkness without blurring foreground action or changing navigation. |

This mapping is an implementation proposal. Epic documents Static Mesh instancing as a way to share repeated geometry and reduce Actor overhead, and Niagara as its principal VFX system. Neither guarantees the present look automatically. [Instanced Static Meshes](https://dev.epicgames.com/documentation/en-us/unreal-engine/instanced-static-mesh-component-in-unreal-engine), [Niagara](https://dev.epicgames.com/documentation/en-us/unreal-engine/creating-visual-effects-in-niagara-for-unreal-engine).

An importer should retain the current hidden-face removal and greedy mesh output, then build reusable native assets. Geometry Scripting offers mesh creation/editing and Static Mesh conversion, but is Beta; its dynamic components lack several Static Mesh features, including distance fields and instancing. Prefer cooking imported static geometry over rebuilding every voxel during play. [Epic Geometry Scripting guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/geometry-scripting-users-guide-in-unreal-engine).

The coordinate adapter needs explicit tests: Defender is Y-up; Unreal uses left-handed Z-up. Convert positions, pivots, normals, rotations, parent matrices and triangle winding consistently. Choose one physical scale before tuning lights and GI, and apply it to speeds, ranges, collision margins and camera distances. Merely swapping two position coordinates is insufficient. [Epic coordinate-system reference](https://dev.epicgames.com/documentation/en-us/unreal-engine/coordinate-system-and-spaces-in-unreal-engine).

**Behaviour is the most important porting boundary.** Keep the authored routes and deployment geometry rather than allowing default navigation or physics to redefine movement. Port the 120-Hz combat accumulator, spawn/exit ordering, pause semantics, horizontal range, muzzle LOS, conservative damage claims, committed bursts and missile guidance explicitly. Compare event traces against the current implementation. Matching model appearance while changing one of these could alter an entire campaign's balance. [Current combat contract](../../combat.md), [engine timing](../../engine.md).

The intended baseline includes the latest requested corrections: immediate overview/Drone changes, shorter steering bursts with synchronized lights and eased rotation, slimmer missile-impact presentation, reduced muzzle light, shorter enemy-death light, roster grouping/range previews and richer distant vistas. Those requests were authorized for current-engine work while this research continued; use their resulting reviewed state, not rejected transitional behaviour. Running/galloping remains withdrawn; audio research does not authorize playback. [Current TODO](../../../TODO.md).

**Unreal is promising for indirect colour, but needs a visual proof.** Lumen provides dynamic diffuse interreflection and colour bleeding, so grass tinting adjacent rock is within its intended capabilities. That makes it a strong candidate for the effect our isolated probe experiment approximates poorly. It is not evidence that this particular scene will look right or run faster. [Epic Lumen overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-global-illumination-and-reflections-in-unreal-engine), [our colour audit](../indirect-colour-audit-2026-10-20/README.md).

Asset representation matters: Lumen's Surface Cache and software distance fields have coverage, thin-surface and modularity constraints. Check merged terrain, small emissive panels, moving rigid parts and instanced foliage in the relevant diagnostic views. Instancing support in one rendering path does not establish equivalent GI representation in every path. Our `castsLight` opt-in also needs deliberate handling so unflagged emissive faces do not acquire unintended illumination. [Epic Lumen technical details](https://dev.epicgames.com/documentation/en-us/unreal-engine/lumen-technical-details-in-unreal-engine).

On Mac, Epic lists software Lumen for Apple Silicon M1+, while hardware ray tracing/MegaLights and Nanite/Virtual Shadow Maps have chip-specific Experimental/Beta qualifications. Hardware and supported Xcode versions must be checked before implementation. No performance claim follows from the feature list or from another platform's demonstration. [Epic macOS requirements](https://dev.epicgames.com/documentation/en-us/unreal-engine/macos-development-requirements-for-unreal-engine).

**Delivery would change.** Unreal supports packaged Windows, macOS and Linux applications. Browser access through Pixel Streaming runs the game and renderer remotely and streams video/input; it introduces hosting, network and latency requirements. It does not preserve our existing local WebGPU browser delivery. This study does not establish a supported native UE5 browser export. Keeping local browser execution as a requirement would materially weaken the case for migration. [Epic packaging](https://dev.epicgames.com/documentation/en-us/unreal-engine/packaging-your-project), [Pixel Streaming architecture](https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-pixel-streaming-in-unreal-engine).

**A bounded next proof, if separately commissioned:**

1. Import A1 and representative scenery, Gun, Dog and Missile assets. Check dimensions, counts, materials, pivots and exact routes against source data and fixed-camera captures.
2. Reproduce one playable wave with placement, upgrades, economy, misses, pause, settling and fresh retry. Match recorded combat events; add a controlled missile case without altering the ordinary wave.
3. Reproduce overview/Drone behaviour, GUI and selected effects. Compare day/night grass-to-rock transport with a neutral-grass control; inspect leaks, emissive opt-ins, background softness and gameplay readability.
4. Build packaged Mac and Windows smoke tests on suitable hosts. Measure CPU/GPU frame time, memory, load time and representative effect peaks; verify gameplay without an editor or MCP server.

Only after those pass should the team estimate the remaining campaign and tooling work. The lead would own one mutating editor session; specialists could work in parallel on separate source modules, import data, art specifications and independent review. This avoids competing edits to the same live assets while retaining team throughput. The present WebGPU game and active playthrough remain the reference and rollback throughout any proposed trial.
