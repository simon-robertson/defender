## Technical constraints

- Target desktop web browsers with WebGPU. Use no third-party dependencies. Do not add libraries, frameworks, engines, CDN packages, or package-based tooling without an explicit change to this requirement.
- Use Bun locally, including its HTTP server when a server is needed.
- Use only the built-in Chrome available through Codex's browser tools. Do not launch or automate system Chrome, Safari, Firefox, or any other external browser. If the built-in browser is unavailable, report that limitation.
- After changes that affect the game, check whether its preview is already open in the built-in browser. **Only open the preview if it is not already open.** Otherwise reuse and refresh the existing tab when changed code/assets need loading; do not create duplicate tabs. Show the relevant zone/view, verify it loaded, and leave it open. This is the user's latest standing instruction and needs no repeated permission.
- The world is grid based. Geometry is authored as axis-aligned quads forming cubes and other shapes; the voxel appearance does not imply a voxel-volume renderer.
- A single grid cell measures 1 unit along each axis. The larger placement grid consists of boxes measuring 24 × 24 × 24 units (XYZ), used to place models, pathways, and other level elements. A model's width and length must each be at most 24 units; its height may exceed 24 units.
- Axis alignment applies in model or part authoring space. Whole models and individual parts may rotate during gameplay, including turret guns.
- Support model rigging and articulated animation, including arms and legs. The workshop uses rigid-part hierarchies and pivots; `engine/rig.js` now animates these with reused matrices and changed-part uploads.
- Game models must remain texture-free to preserve the visual style. Textures for visual effects are explicitly approved when needed; GUI textures are also allowed. GPU textures used as render targets, depth buffers, or other rendering data remain allowed. Permission to use effect textures does not approve unrelated effects.
- Faces carry colour, emission (the stored name for luminance), and reflectiveness. Both emission and reflectiveness range from 0 to 1. Preserve all properties through authoring, meshing, and export. The optional `castsLight` flag explicitly opts an emissive face into local lighting; emission alone does not.
- Current appearance decision: **water and rain-wet paths are reflective**. Zone A uses rain when its per-level author switch is enabled; rainy path stone/mortar use reflectiveness 0.4/0.1, with broken blue-grey edge puddles at 0.85. Every active model material, including per-face override materials, uses reflectiveness 0. New-model and generator defaults must stay at 0 until the user approves otherwise; preserve the format's 0–1 capability for later use.
- Keep meshes clean to avoid z fighting. Author on a 3D cell grid, reject overlapping cells, remove hidden faces within rigid parts, and merge matching exposed faces. Retain interfaces that must be exposed when articulated parts move. Never hide modelling errors with depth bias or duplicate coplanar surfaces.
- Levels may extend outside the viewport; camera panning must accommodate large levels. The visual preview uses an orthographic orbit/pan/zoom camera, plus an approved `F`-toggled path view: random path-box start, perspective FOV 80°, WASD movement, mouse rotation (dragging for development), no model collisions, always 12 units above terrain ground. `F` restores the previous overview. Final gameplay camera decisions remain open.
- Keep future Web Audio API integration in mind. Do not add audio playback, sound, or music yet.
- Approved rendering requirements: an initial depth-only pass, dynamic lighting with at least one shadow-casting sky light per level, opt-in light emission from flagged model faces, SSR, particles, and instancing where possible. One-bounce indirect lighting remains tentative. See [the rendering requirements](project-docs/rendering.md).
- Main terrain regions, including streams, must align to the 24 × 24 box grid from above. Ground height and water depth change in 1-unit vertical steps; enemy path boxes remain flat and dry at one common height. See [terrain authoring](project-docs/terrain.md).
- Latest path-art direction: larger irregular slabs instead of small regular tiles. Use staggered joints, occasional orthogonal stepped/L-shaped edges and subtle whole-slab shade variation; keep the route footprint box aligned and flat. The shared world-space pattern continues across box boundaries in every zone. See [path surfaces](project-docs/path-surfaces.md).
- Default level ground is one box (24 units) high, with carve-outs for lakes/streams and higher scenery mounds. Latest decision: all player defences must sit on ground at the enemy path height; this supersedes earlier approval for raised defence mounds. Mark player defence models with `role: "defence"`. Time of day and weather are fixed author settings per level; no day/night cycle or dynamic weather transitions. ## Performance priorities

- Consider compact data storage, batching, visibility handling, and efficient GPU uploads when designing an approved feature. Choose concrete strategies from measured needs.

- Do not invent frame-rate targets, hardware baselines, entity limits, or benchmark results. Agree budgets before using them as acceptance criteria.
